📋 Agent Operating Policies (AOP) — Developer Guide

FlowAMP — AI Agent Governance on AWS · What the AOP tab actually is today, and what a real enforcement engine would require

⚠️ Read this first — AOP is a demo/illustrative surface. In FlowAMP today the AOP tab is a catalog of sample policies: descriptive metadata plus a hand-authored workflow diagram per policy. There is no AOP enforcement engine, no work-item runtime, and no write path for AOPs in this repo. Nothing here triggers agents, checks guardrails, or escalates to a human at runtime. The "Demo → Production" and "AgentCore-Native AOP Enforcement" sections below describe an aspirational future design — they are not built.
What is an AOP (conceptually)? An Agent Operating Policy is meant to define when an agent activates, what it's allowed to do, which guardrails constrain it, and when it must escalate to a human. In FlowAMP it currently exists only as descriptive metadata surfaced in the UI. Turning it into an enforceable runtime contract (EventBridge rules, Bedrock Guardrails, Step Functions, scoped IAM) is future work.

Where the AOP tab data actually comes from

The AOP tab is rendered entirely client-side from a hardcoded JavaScript array — it does not call the backend. In assetsSrc/site/agent-management.html:

  • const aopsData = [ … ] — 14 sample policies (AOP-01…AOP-14), baked into the page.
  • renderAops(filter) renders cards straight from aopsData; filterAops / toggleAop / toggleEntry just filter and expand it.
  • saveAopEdit(id) ("✏️ Edit Workflow") mutates the in-memory array only and calls a client-side logAudit — nothing is persisted; a page reload discards the change.

There is a separate GET /aops REST route (see below), but the AOP tab does not consume it — the numbers you see in the UI are the hardcoded array, not DynamoDB.

Backend model & the GET /aops route DEMO / SEED-ONLY

FlowAMP uses a single DynamoDB table (AgentTable, PK agentId + SK sk). AOP rows are stored under the aop: prefix with sk = "INFO". The data-handler Lambda exposes a read-only route (assetsSrc/lambda/data-handler/index.py, wired in cdk/lib/team-stack.ts):

# assetsSrc/lambda/data-handler/index.py
if path.endswith('/aops'):
    return _resp(200, _project(get_by_prefix('aop:'), _AOP_FIELDS))

# Only these fields are ever returned:
_AOP_FIELDS = {'agentId', 'aopId', 'name', 'status', 'agents', 'executions',
               'successRate', 'owner', 'entry'}

A DynamoDB AOP row (as seeded) looks like:

{
  "agentId":     "aop:AOP-01",   // partition key (PK), sk = "INFO"
  "aopId":       "AOP-01",
  "name":        "Service Degradation Response",
  "status":      "active",        // "active" | "draft" | "review"
  "agents":      "Service Health Monitor, Incident Prediction Agent",  // comma-joined string
  "executions":  12450,           // static seed value
  "successRate": 97.8,            // static seed value (Decimal in the table)
  "owner":       "Operations",
  "entry":       "Service latency exceeds SLA threshold for 5 consecutive minutes"
}

Two things to be honest about here IMPORTANT

  1. These rows only exist when seedSampleData=true, which defaults to FALSE. They are written once by the seed-data Lambda (assetsSrc/lambda/seed-data/index.py, AOP_DATA). A default production deploy has zero AOP rows, so GET /aops returns [].
  2. There is no AOP write path. The data-handler's only write routes are POST /agents, PATCH /agents/{agentId}, and POST /agents/{agentId}/lifecycle — all for agents. AOPs can only be created by re-running the seed Lambda; the UI cannot create, edit, or delete an AOP in DynamoDB.

Note the UI's hardcoded aopsData array and the seed AOP_DATA are separate copies of the same 14 sample policies. The AOP tab renders the JS array; it does not fetch /aops.

The AOP / work-item runtime is intentionally stubbed STUBBED

FlowAMP's governance agents (discovery-scanner, compliance-scanner) reference an AOP/work-item runtime that is not part of this deployment. Those work-item tools are safe no-ops. From the repo README (Notes):

"Their AOP / work-item orchestration is intentionally stubbed (no work-item runtime here), so those tools are safe no-ops."

And from assetsSrc/agents/_shared/flowamp_tools/work_items.py:

"This repo has no AOP runtime and no WorkItemTable, so the governance agents run in one-shot mode (invoked directly, no workItemId). … they are provided here as safe no-ops: each logs its call and returns well-formed JSON, but writes nothing."

Concretely: create_work_item / close_assigned_work_item in compliance-scanner/tools.py and flowamp_tools/work_items.py return synthetic, non-persisted IDs. The finalize_audit escalation path preserves the call shape "so a future AOP runtime" could be wired in, but today nothing is dispatched, held, or escalated.

The one place AOPs feed a live behavior: the compliance scorer

The compliance checks package defines an aop-coverage transparency check (assetsSrc/agents/_shared/flowamp_compliance_checks/checks/transparency.py, class AopCoverage): "at least one active AOP references this agent." It reads an AOP_TABLE_NAME environment variable and queries for AOP rows referencing the agent. In this single-table repo that env var is not wired to a dedicated AOP table, so the check degrades to a "not set / cannot check" evidence result rather than a real coverage signal. It is scored (e.g. NIST AI RMF Govern, baseline transparency) but should be read as illustrative given the seed-only AOP data.

Demo → Production: What an Enforcement Engine Would Add

Everything below this line is aspirational / not built. It documents the design a real AOP enforcement engine would need — none of these AWS resources are created by FlowAMP today.

What FlowAMP does today DEMO

AOPs are descriptive metadata — a hardcoded UI array (and optional seed rows in DynamoDB) with name, agents, a trigger condition as a text string, and static execution/success numbers. The frontend renders them as cards with expandable flow diagrams. Nothing enforces the policy at runtime, and there is no work-item dispatch, escalation, or write path.

What a production enforcement engine would need NOT BUILT

Each AOP becomes an enforceable runtime contract composed of AWS primitives:

  • Trigger → EventBridge Rule (pattern match on IoT, CloudWatch Alarm, schedule, or API call)
  • Decision → Bedrock Agent invocation with constrained prompt + Guardrails
  • Action → Lambda execution with scoped IAM role (least-privilege per AOP)
  • Guardrail → Bedrock Guardrail with AOP-specific content/topic/PII filters
  • Escalation → SNS → PagerDuty / human-in-the-loop approval via Step Functions
  • Audit → CloudTrail + DynamoDB execution log with full trace

Example: AOP-03 Hypothetical Enforcement Flow NOT BUILT

Network Intrusion Detection — how enforcement would flow when anomalous network traffic is detected (illustrative — FlowAMP does not run any of this):

① TRIGGER — EventBridge
Security signal published → EventBridge rule aop-03-trigger matches pattern {"source": ["aws.securityhub"], "detail": {"signalType": ["network_traffic"]}}
② GUARDRAIL CHECK — Pre-Invocation
Before invoking agent: verify AOP is active, check cost budget not exceeded, validate input against Bedrock Guardrail gr-secops-001 (block PII, enforce content filters)
③ DECISION — Bedrock Agent
Network Anomaly Detector agent analyzes traffic pattern. Uses action group tools: query_traffic_baseline, compare_known_signatures, assess_threat_level. Returns confidence score + severity.
④ ESCALATION GATE — Step Functions
If confidence < 0.85 OR severity == 'critical' → pause execution, send SNS to SecOps on-call, wait up to 15 min for human approval. Timeout → execute isolate_network_segment automatically.
⑤ ACTION — Lambda (scoped IAM)
Incident Response Agent creates incident ticket, logs to DynamoDB, sends CloudWatch metric. IAM role only allows dynamodb:PutItem, sns:Publish, cloudwatch:PutMetricData. Cannot touch EC2, IAM, or S3.
⑥ AUDIT — CloudTrail + DynamoDB
Full execution trace written: trigger event, agent reasoning (Bedrock trace), guardrail checks, escalation decision, action taken, latency, cost. Retained per the applicable compliance retention requirement.

CDK Implementation (reference design) NOT BUILT

None of the constructs below exist in FlowAMP's CDK today (there is no AOPEngine state machine, no aop-validator Lambda, and no per-AOP EventBridge rules or IAM roles). This is a blueprint for what an enforcement engine would add.

AOP Enforcement Engine (Step Functions + EventBridge)

// For each active AOP, create an EventBridge rule → Step Function → Agent
const aopEngine = new sfn.StateMachine(this, 'AOPEngine', {
  definitionBody: sfn.DefinitionBody.fromChainable(
    // Step 1: Validate AOP is active + budget check
    new tasks.LambdaInvoke(this, 'ValidateAOP', {
      lambdaFunction: aopValidatorFn,
      resultPath: '$.validation',
    })
    // Step 2: Pre-invocation guardrail check
    .next(new sfn.Choice(this, 'AOPActive?')
      .when(sfn.Condition.stringEquals('$.validation.Payload.status', 'blocked'),
        new sfn.Fail(this, 'AOPBlocked', { cause: 'AOP inactive or budget exceeded' }))
      .otherwise(
        // Step 3: Invoke Bedrock Agent
        new tasks.LambdaInvoke(this, 'InvokeAgent', {
          lambdaFunction: agentHandlerFn,
          resultPath: '$.agentResult',
        })
        // Step 4: Escalation gate
        .next(new sfn.Choice(this, 'NeedsEscalation?')
          .when(sfn.Condition.or(
            sfn.Condition.numberLessThan('$.agentResult.Payload.confidence', 0.85),
            sfn.Condition.stringEquals('$.agentResult.Payload.severity', 'critical')),
            // Human approval with timeout
            new tasks.SnsPublish(this, 'EscalateToHuman', {
              topic: escalationTopic,
              message: sfn.TaskInput.fromJsonPathAt('$.agentResult.Payload'),
            }).next(new tasks.CallAwsService(this, 'WaitForApproval', {
              service: 'sfn', action: 'getActivityTaskOutput',
              // ... approval wait logic with 15-min timeout
            })))
          .otherwise(
            // Step 5: Execute action
            new tasks.LambdaInvoke(this, 'ExecuteAction', {
              lambdaFunction: actionExecutorFn,
              resultPath: '$.actionResult',
            })))
        // Step 6: Audit log
        .next(new tasks.DynamoPutItem(this, 'AuditLog', {
          table: agentTable,
          item: { /* execution trace */ },
        }))
      )
    ),
  timeout: cdk.Duration.minutes(20),
});

// Create EventBridge rules for each AOP trigger pattern
// Example: AOP-03 Network Intrusion Detection trigger
new events.Rule(this, 'AOP-03-Trigger', {
  eventPattern: {
    source: ['aws.securityhub'],
    detailType: ['Network Anomaly Alert'],
    detail: { signalType: ['network_traffic'] },
  },
  targets: [new targets.SfnStateMachine(aopEngine, {
    input: events.RuleTargetInput.fromObject({
      aopId: 'AOP-03',
      event: events.EventField.fromPath('$.detail'),
    }),
  })],
});

AOP Validator Logic

def handler(event, context):
    aop_id = event['aopId']
    aop = table.get_item(Key={'agentId': f'aop:{aop_id}'}).get('Item')

    if not aop or aop.get('status') != 'active':
        return {'status': 'blocked', 'reason': 'AOP not active'}

    # Budget check — has this AOP exceeded its daily cost limit?
    boundaries = json.loads(aop.get('boundaries', '{}'))
    max_cost = boundaries.get('maxCostPerExecution', 1.0)
    today_cost = get_today_cost(aop_id)
    daily_limit = max_cost * 1000  # max 1000 executions/day at max cost
    if today_cost >= daily_limit:
        return {'status': 'blocked', 'reason': 'Daily cost limit exceeded'}

    # Version check — ensure latest approved version
    if aop.get('approvedBy') is None:
        return {'status': 'blocked', 'reason': 'AOP not approved'}

    return {
        'status': 'allowed',
        'aop': aop,
        'guardrailId': aop.get('guardrails', {}).get('guardrailId'),
        'agents': aop.get('agents', []),
        'escalation': aop.get('escalation', {}),
    }

AOP Lifecycle

StatusMeaningEnforcement
draftPolicy being authored. No trigger, no execution.EventBridge rule does not exist. Agent cannot be invoked under this AOP.
reviewSubmitted for approval. May run in shadow mode.EventBridge rule exists but targets a shadow Step Function that logs but does not act. Metrics collected for evaluation.
activeApproved and enforced. Full execution.EventBridge rule targets production Step Function. All guardrails, escalations, and boundaries enforced.
suspendedTemporarily disabled (incident, budget, audit).EventBridge rule disabled. Existing in-flight executions complete but no new triggers accepted.
decommissionedPermanently retired.EventBridge rule deleted. DynamoDB record retained for audit (retention per boundaries.retentionDays).

💡 Key Insight: The AOP is intended to be the bridge between governance (what agents should do) and runtime (what agents actually do), so that every agent invocation traces back to an AOP. FlowAMP today only models the governance half (the catalog + the aop-coverage transparency check); the runtime enforcement half is not built. An agent without an AOP is an ungoverned agent — a real enforcement engine would flag it and drop the NIST AI RMF "Govern" function score.

Cedar Policy Example: AOP-05 Daily Risk Position Review (illustrative)

// AOP-05: Risk agent can review positions but with constraints
permit(
  principal == Agent::"portfolio-risk",
  action == Action::"invoke_tool",
  resource == Tool::"get_position"
);

permit(
  principal == Agent::"portfolio-risk",
  action == Action::"invoke_tool",
  resource == Tool::"adjust_position"
) when {
  context.notional_usd <= 1000000 &&        // max $1M per adjustment
  context.risk_limit_ok == true &&          // within pre-set risk limits
  context.market == "close_of_business"      // only at market close, not intraday
};

forbid(
  principal == Agent::"portfolio-risk",
  action == Action::"invoke_tool",
  resource == Tool::"adjust_position"
) when {
  context.notional_usd > 1000000           // large adjustments need human approval
  && !context.human_approved
};

// Risk agent cannot access privileged access-control tools
forbid(
  principal == Agent::"portfolio-risk",
  action == Action::"invoke_tool",
  resource in [Tool::"grant_admin_access", Tool::"disable_firewall", Tool::"revoke_credentials"]
);

This single Cedar policy would replace: the EventBridge trigger rule, the Step Functions state machine, the AOP validator Lambda, the scoped IAM role with explicit deny, and the SNS escalation — all in ~25 lines of declarative policy.
