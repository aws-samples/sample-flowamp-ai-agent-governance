🏛️ Compliance Auditing — FlowAMP Developer Guide

FlowAMP AI Agent Governance · How the compliance-scanner produces real A–F audit grades

Context: FlowAMP grades every governed agent against compliance frameworks using the compliance-scanner — an AgentCore Runtime (a Strands agent on us.anthropic.claude-sonnet-4-6) that combines a deterministic checks library with LLM judgement. This is real and wired end-to-end: on a daily schedule and on demand, the scanner runs ~23 deterministic checks across five frameworks, authors a narrative + recommendations, and writes an AUDIT#<ts> row (plus a projected lastAuditedAt) that the UI reads back as an A–F grade. This guide documents the current implementation and flags the parts that are still stubbed for production hardening.
✅ Real now vs. 🟡 still-to-harden. Badges throughout this doc mark what is live: REAL the compliance-scanner runtime, the deterministic checks, the audit row shapes, the triggers, the read APIs, and the Compliance UI. STUB a handful of dependencies are safe no-ops in this single-table deployment: work-item lifecycle tools, Athena/curated-warehouse trend checks, and the escalation/AOP runtime. Compliance frameworks are code-defined — runtime editing is not supported.

Data Model

FlowAMP uses a single DynamoDB table (AgentTable, partition key agentId, sort key sk). Row types are separated by sk prefix. The compliance-scanner writes these:

Row (sk)Written byMeaning
AUDIT#<ts>finalize_audit → write_audit_reportOne compliance audit report per run (rowType="AUDIT").
RAI#<ts>write_rai_scoreResponsible-AI sub-scores + composite in [0.0, 1.0].
EVENT#<ts>#<id>log_compliance_eventcompliance_audit event with a 90-day TTL; surfaces in the Event Explorer.
COMPLIANCE#<frameworkId>seed / operatorsPer-agent framework assignment (opt-in beyond the baseline).
INFO (projection)_update_agent_last_auditedConditional SET lastAuditedAt on the agent's INFO row — never overwrites a newer timestamp.

The AUDIT# report shape REAL

Every audit row carries a report object with exactly these keys (validated in write_audit_report). Floats are coerced to Decimal at the DynamoDB boundary:

  "createdAt":"2026-07-06T04:00:12Z",
  "report": {
    "byFramework": {                       // one entry per applicable framework

        "grade": "B",                      // computed from the rubric (see below)
        "criticalFailures": 1,
        "highFailures": 2,

Letter grades

Grades come from the framework's auditorConfig.gradingRubric (all five frameworks ship the same rubric). _score_to_grade walks thresholds high→low; below the lowest returns F:

A+ ≥ 0.95 · A ≥ 0.85 · B ≥ 0.75 · C ≥ 0.65 · D ≥ 0.50 · F < 0.50

Triggers

Why a fire-and-forget invoker? REAL

The compliance-scanner is an AgentCore Runtime (invoke-only, no API of its own) and — being an LLM auditor running deterministic checks per agent — takes minutes. API Gateway's hard integration timeout is 29 s, so it cannot be invoked synchronously behind the API. The compliance-scan-invoker Lambda bridges the gap:

  • API path (POST /compliance/scan): reads an optional {"agentId": "..."} body, async re-invokes itself with InvocationType='Event', and returns HTTP 202 {"status":"started"} immediately.
  • Async worker ({"async_audit": true, "agentId": ...}): performs the long invoke_agent_runtime call and drains the response so the runtime finishes.
  • EventBridge schedule (daily): arrives as {"source": "aws.events"} → treated as a rotation run, same async path.

Daily rotation (EventBridge, 04:00 UTC) REAL

The ComplianceAuditSchedule rule fires once a day and audits one agent per run — the eligible agent with the oldest lastAuditedAt. Selection (_pick_rotation_target) sorts eligible agents ascending by lastAuditedAt, treating absent/null as "" so never-audited agents win first. _eligible_for_audit skips FLOWAMP_ sentinel rows and decommissioned/rejected agents. Candidates can optionally be restricted to specific platforms by adding FLOWAMP_PLATFORMS rows flagged auditable=true; nothing writes those rows by default, and their absence means "audit everything eligible" — earlier versions treated an empty allowlist as "no candidates", which made every rotation run a silent no-op that still reported success. The cursor is pre-stamped before the LLM loop runs, so a flaky audit can never park the rotation on the same agent forever (ADR-22).

On-demand REAL

POST /compliance/scan {"agentId": "..."} audits one specific agent; POST /compliance/scan {} triggers a rotation pick. The UI's per-agent "Run audit" / "Re-audit" buttons send the agent id; the "Run rotation audit" button sends {}.

// cdk/lib/team-stack.ts — daily rotation schedule
new events.Rule(this, "ComplianceAuditSchedule", {
  schedule: events.Schedule.cron({ minute: "0", hour: "4" }),   // 04:00 UTC
  description: "Daily compliance audit — one agent per run (oldest lastAuditedAt first)",
}).addTarget(new targets.LambdaFunction(complianceScanInvokerFn));

// POST /compliance/scan → compliance-scan-invoker (fire-and-forget)
complianceResource
  .addResource("scan")
  .addMethod("POST", new apigateway.LambdaIntegration(complianceScanInvokerFn));

The Deterministic Checks Framework

flowamp_compliance_checks is a shared library used by both the compliance-scanner (via the run_check tool) and the RAI Scorer. Each check is a Check subclass registered at import time; the auditor calls run_check(checkId, target, params) and results are cached per run so duplicate checks across frameworks cost nothing. Convenience base classes handle common shapes: AthenaCheck (trend queries), AwsConfigCheck (Config compliance), IamPolicyCheck (role policy inspection). A CheckResult is {result: pass|fail|skip, evidence, duration_ms, requiresWorkItem}.

The ~23 built-in checks span five categories. AccessDenied and unavailable dependencies return skip (not fail), so missing IAM or absent Athena degrades gracefully rather than tanking a grade:

CategoryChecks (checkId · default severity · cost)
fairnessguardrail-attached (high) · guardrail-content-policy (high) · guardrail-intervention-rate (high, moderate) · invocation-log-pii-sample (high, expensive) · user-feedback-rate (medium, moderate)
transparencybedrock-invocation-logging (high) · agent-log-group-exists (medium) · cloudtrail-bedrock-coverage (medium, moderate) · aop-coverage (medium) · agent-trace-enabled (medium) · decisions-logged (medium)
accountabilityowner-populated (high) · escalation-group-assigned (high) · dlq-configured (medium) · lambda-error-rate (high, moderate) · agent-staleness (medium) · cw-alarms-cover-agent (medium) · tagging-compliance (low)
ethicsguardrail-sensitive-info-policy (high) · guardrail-topic-policy (medium) · model-on-approved-list (high)
operationalvpc-isolated (high) · data-residency-region (critical) · audit-frequency (medium) · appconfig-model-selection (low)

DATA GAP This deployment has no historical Athena / curated warehouse. The moderate/expensive trend checks (guardrail-intervention-rate, invocation-log-pii-sample, cloudtrail-bedrock-coverage, lambda-error-rate, user-feedback-rate) and the query_athena tool return no rows with an explanatory note. The system prompt instructs the auditor not to treat an empty Athena result as a finding — audits are grounded in the cheap checks, read_past_audits, and read_past_overrides. Hardening = stand up the invocation-log warehouse and wire the trend queries.

Compliance Frameworks (code-defined)

FlowAMP ships five frameworks in flowamp_compliance_checks/frameworks. Each framework is a code dict declaring a raiConfig (per-dimension checks + weights, used by the RAI Scorer), an auditorConfig (extra auditor-only checks + grading rubric + prompt guidance), and escalations rules. list_applicable_frameworks(agentId) always includes FLOWAMP_BASELINE, then layers any per-agent COMPLIANCE# assignment rows on top.

FLOWAMP_BASELINE — FlowAMP Baseline
Organisational baseline applied to every agent. References the cheap-tier checks across all four RAI dimensions + auditor checks (tagging, audit-frequency, appconfig-model-selection). Owns the composite grading rubric.
nist-ai-rmf — NIST AI RMF
GOVERN / MAP / MEASURE / MANAGE alignment. Guardrail + logging + ownership + escalation checks; auditor adds audit-frequency.
iso-27001 — ISO/IEC 27001
Information-security management for AI agents. Adds guardrail-sensitive-info-policy; auditor adds vpc-isolated + tagging-compliance.
soc-2 — SOC 2
Trust Service Criteria (Security, Availability, Confidentiality). DLQ + alarms + logging + sensitive-info checks; auditor adds audit-frequency + tagging-compliance.
nerc-cip — NERC CIP
Critical Infrastructure Protection for grid-operations agents. Guardrail + logging + alarms + approved-model checks; auditor adds vpc-isolated + data-residency-region (critical) + audit-frequency.

STUB Frameworks are code-defined — there is no ComplianceFrameworkTable and runtime editing of frameworks is not supported. To add or change a framework you edit the templates in flowamp_compliance_checks/frameworks/ and redeploy. Per-agent framework assignment (which frameworks apply to a given agent) is data-driven via COMPLIANCE# rows.

How the Scanner Runs an Audit

The scanner (compliance-scanner/main.py) is a Strands Agent exposed through BedrockAgentCoreApp. The invoke(payload) entrypoint accepts two shapes:

  • On-demand: agentId in the payload top-level → audit that agent.
  • Rotation: no agentId → _pick_rotation_target() selects the oldest-audited eligible agent. (A work-item-driven dispatch shape is also accepted but its lifecycle tools are no-ops here — there is no AOP/WorkItem runtime in this repo.)

In both paths lastAuditedAt is pre-stamped, then the Strands loop runs under the system prompt with these tools:

ToolKindPurpose
get_agentreadINFO record + COMPLIANCE# assignments.
list_applicable_frameworksreadResolved framework dicts (always includes baseline).
run_checkreadExecute a deterministic check (cached per run).
read_past_audits / read_past_overridesreadHistory for pattern-aware judgement (don't re-flag resolved overrides).
list_agent_data_access / list_agent_tool_accessreadAccess-matrix grants + sensitivity metadata for sensitivity-vs-label reasoning.
query_athenareadTrend queries — STUB returns no rows in this deployment.
add_audit_notewriteDrop a NOTE# row during the reasoning loop.
create_work_itemwriteEscalation work item — STUB no-op (no WorkItem runtime).
finalize_auditwriteThe single atomic commit — writes the AUDIT# row, event, and escalations.

The system prompt constrains the auditor tightly: it may not write to the AgentTable directly, invoke other runtimes directly, or use raw boto3 — every mutation flows through finalize_audit, add_audit_note, or create_work_item. It reasons about sensitivity mismatches (e.g. an agent holding restricted data but declaring public output) and surfaces them in the narrative rather than auto-escalating.

# compliance-scanner/main.py — the atomic commit tool signature
finalize_audit(
    agentId,
    byFramework,      # {frameworkId: {score, criticalFailures, highFailures, checks[]}}
    narrative,        # ≤ 4000 chars
    recommendations,  # [{checkId, severity, recommendation, frameworks[]}]
    escalations,      # [{group, criteria, title, priority, payload}]
)
# finalize_audit then: validates inputs → computes per-framework + composite grades
# against the baseline rubric → write_audit_report(AUDIT#) → log_compliance_event
# → create work items (no-op) → patch escalatedWorkItems → returns {auditSk, ...}.

Read Paths & the Compliance UI

Data-handler read APIs REAL

  • GET /agents/{agentId}/audit?limit=N → get_agent_audits: a single-partition Query on AUDIT# with ScanIndexForward=False (newest-first). Cheap, no scan.
  • GET /audits → get_all_latest_audits: one scan for AUDIT# rows, reduced to the newest row per agentId (the lexical sk max). Backs the fleet Compliance view.

Both responses are projected to _AUDIT_FIELDS = {'agentId', 'sk', 'rowType', 'createdAt', 'report'} — anything not in that set (including internal keys) is dropped before it reaches the browser.

UI surfaces REAL

In agent-management.html the compliance data drives two views:

  • Dedicated "Compliance" sidebar view (loadComplianceFleet / renderComplianceFleet): a fleet table with the composite A–F grade, composite score /100, per-framework badges, the top critical/high failed checks, and the last-audited date. A summary strip shows the grade distribution (graded / passing A–B / marginal C / failing D–F). "Run rotation audit" (runFleetAudit → POST /compliance/scan {}) and per-row "Re-audit" (runComplianceAudit → POST /compliance/scan {agentId}) trigger scans and poll the view until the new grade lands. Auto-refreshes every 60 s.
  • Per-agent Compliance Audit panel in the agent detail Overview tab (loadAgentAudit → GET /agents/{id}/audit?limit=1): shows the agent's newest composite grade, per-framework grades, and a "Run audit" button. After triggering, it polls loadAgentAudit a few times so the panel updates once the scanner's new AUDIT# row lands (~1–2 min).
