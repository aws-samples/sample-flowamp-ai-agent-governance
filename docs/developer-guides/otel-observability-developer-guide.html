🔭 OpenTelemetry & AgentCore Observability — Developer Guide

FlowAMP · How agent traces get from a Strands agent to aws/spans, and how the pipeline is wired for AgentCore Evaluations

Overview: AgentCore Evaluations (the Evaluations page) scores agents by reading their OpenTelemetry spans, not their application logs. This guide describes how a Strands agent deployed with direct-code deployment emits those spans, the end-to-end data flow to CloudWatch, and how the pipeline is configured.

The pipeline at a glance

Strands agent (native OTEL instrumentation)
   │  spans: chat / execute_tool / execute_event_loop_cycle …
   ▼
opentelemetry-instrument bootstrap  ── installs global TracerProvider + ADOT exporter
   │  (activated by AGENT_OBSERVABILITY_ENABLED; see "Enabling instrumentation")
   ▼
OpenInference processor  ── rewrites Strands spans into GenAI semantic conventions
   │
   ▼
AgentCore Runtime collector ──► CloudWatch  aws/spans  (Transaction Search index)
   │
   ├──► AgentCore Observability (GenAI Observability console)
   └──► AgentCore Evaluations (online eval config samples a session, LLM-judges it)
              │
              ▼
        /aws/bedrock-agentcore/evaluations/results/<config-id>  +  EMF metrics
              │
              ▼
        FlowAMP data-handler  →  GET /evaluations  →  Evaluations UI

Enabling instrumentation on the direct-code runtime

OpenTelemetry auto-instrumentation is activated by launching the agent under the opentelemetry-instrument command — this reads the OTEL environment variables and installs a global TracerProvider wired to the runtime's collector. On the container deployment path this is set in the Dockerfile:

CMD ["opentelemetry-instrument", "python", "main.py"]

FlowAMP uses direct-code deployment (zip → S3, no Docker), where the runtime launches the entrypoint directly as python main.py and the auto-instrumentation command is not applied. Without it, the global provider remains a ProxyTracerProvider, OTEL_EXPORTER_OTLP_ENDPOINT is not configured, and no spans are exported to aws/spans.

Activate auto-instrumentation from code. Each main.py re-execs itself once, in-process, invoking the auto-instrumentation entry point. Use the importable entry point rather than the opentelemetry-instrument console script — with uv pip install --target the script is installed under <bundle>/bin (not on PATH), so re-exec the runtime interpreter and call the module directly:

import os as _os, sys as _sys

if (_os.environ.get("AGENT_OBSERVABILITY_ENABLED") == "true"
        and not _os.environ.get("_OTEL_REEXEC")):
    _os.environ["_OTEL_REEXEC"] = "1"                      # one-shot guard
    _bundle_dir = _os.path.dirname(_os.path.abspath(__file__))
    _os.environ["PYTHONPATH"] = (_bundle_dir + _os.pathsep
        + _os.environ.get("PYTHONPATH", "")).rstrip(_os.pathsep)
    try:
        _os.execv(_sys.executable, [
            _sys.executable, "-c",
            "from opentelemetry.instrumentation.auto_instrumentation import run; run()",
            _sys.executable, *_sys.argv,
        ])
    except Exception as exc:            # wrapper absent (local dev) → run uninstrumented
        print(f"otel auto-instrument re-exec skipped: {exc}")

MUST be the first thing in the module, before boto3/strands import (auto-instrumentation patches libraries at import). The _OTEL_REEXEC flag makes it a one-shot: the re-exec'd process sees it set, skips the branch, and proceeds to the real imports — now fully instrumented. Guarded so a missing wrapper (e.g. local runs) never crashes the agent.

CDK wiring: the observability env

The re-exec branch is gated on AGENT_OBSERVABILITY_ENABLED, which (with the sibling ADOT vars) is set on every runtime in team-stack.ts and sample-agents-stack.ts:

const observabilityEnv: Record<string, string> = {
  AGENT_OBSERVABILITY_ENABLED: "true",
  OTEL_PYTHON_DISTRO: "aws_distro",
  OTEL_PYTHON_CONFIGURATOR: "aws_configurator",
  OTEL_EXPORTER_OTLP_PROTOCOL: "http/protobuf",
};
// merged into each runtime:
environmentVariables: { AGENT_TABLE_NAME: agentTable.tableName, PORT: "8080", ...observabilityEnv }

These are consumed by the aws_distro configurator that the re-exec activates; the runtime supplies the actual OTLP endpoint internally (it is intentionally not exposed as an env var).

Prerequisite: CloudWatch Transaction Search per account/region

Spans are only indexed into aws/spans when Transaction Search is enabled — a one-time setup per account/region. Without it, agents emit spans but nothing is queryable, and Evaluations produces nothing. Check and enable via API:

# status: "CloudWatchLogs" + "ACTIVE" = enabled; "XRay" = not enabled
aws xray get-trace-segment-destination --region <region>

# enable: (1) allow X-Ray to write spans to CloudWatch Logs
aws logs put-resource-policy --policy-name TransactionSearchXRayAccess \
  --policy-document '{"Version":"2012-10-17","Statement":[{"Sid":"TransactionSearchXRayAccess",
    "Effect":"Allow","Principal":{"Service":"xray.amazonaws.com"},"Action":"logs:PutLogEvents",
    "Resource":["arn:aws:logs:REGION:ACCOUNT:log-group:aws/spans:*",
                "arn:aws:logs:REGION:ACCOUNT:log-group:/aws/application-signals/data:*"],
    "Condition":{"ArnLike":{"aws:SourceArn":"arn:aws:xray:REGION:ACCOUNT:*"},
                 "StringEquals":{"aws:SourceAccount":"ACCOUNT"}}}]}'
# (2) point trace segments at CloudWatch Logs
aws xray update-trace-segment-destination --destination CloudWatchLogs

Status goes PENDING → ACTIVE in a few minutes, and only spans generated after activation are indexed. Because Transaction Search is account/region-scoped — not a stack resource — FlowAMP does not create it in CDK; it's an operator prerequisite. Evaluations are therefore per-account: cross-account agents are scored in the account they run in.

Verifying it works

1. The agent bootstrapped ADOT

In the agent's runtime log group (/aws/bedrock-agentcore/runtimes/<name>-<id>-DEFAULT), a working run shows rich OTEL resource attributes and:

telemetry.auto.version: 0.18.0-aws        # ADOT active (re-exec worked)
aws.service.type: gen_ai_agent
# and the benign: "Attempting to instrument while already instrumented"
#   → the OpenInference processor engaged
# A FAILURE looks like: "otel auto-instrument re-exec skipped: ..."  or a
#   ProxyTracerProvider warning → the wrapper didn't run.

2. Spans reached aws/spans

Do NOT trust storedBytes on the log group — it lags for hours and reads 0 even when spans are flowing. Filter for recent events instead:

aws logs filter-log-events --log-group-name aws/spans \
  --start-time $(( ($(date +%s) - 900) * 1000 )) --max-items 5 --region <region>
# real spans have names like: "chat <model>", "execute_tool <tool>",
# "execute_event_loop_cycle", each with a populated traceId.

FlowAMP's readiness endpoint uses this same recent-events probe (not storedBytes): GET /evaluations → readiness.spansPresent.

3. Scores appear (the slow part)

Even with spans flowing, a score only lands after a covered agent runs a new session (the sampler doesn't backfill old ones), the session completes (its sessionTimeoutMinutes of inactivity), and AgentCore's recurring sampler grades it — typically ~10–30 min end to end. An idle fleet produces no scores.
