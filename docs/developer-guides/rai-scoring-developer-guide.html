🛡️ Responsible AI Scoring — FlowAMP Developer Guide

FlowAMP AI Agent Governance · How RAI scoring works today and what still needs hardening

Context: The rai-scorer Lambda runs once a day on an EventBridge schedule (and on demand via POST /rai/score) and computes four equally-weighted sub-scores — fairness, transparency, accountability, ethics — per registered agent, plus a weighted overall score. It reads real CloudWatch and CloudTrail signals today. But in a fresh account most of those signals do not exist yet: CloudWatch metric queries return 0, CloudTrail lookups return no events, and every sub-score sits at its base value until real agent traffic and guardrail activity accrue. This guide documents exactly what is computed now versus what still needs to be wired up for a production-grade signal, and keeps the honest gap marked with badges.
⚠️ Honest state: RAI scoring is real but partly seed-shaped right now. The scorer executes real API calls, but because a fresh FlowAMP deployment has no accumulated invocation history, guardrail metrics, or CloudTrail volume, the arithmetic collapses to the base constants below. Scores move only once agents are actually invoked, guardrails are attached and intervening, and CloudTrail has 24h of coverage. The UI also seeds an illustrative fleet (aiScoresData in agent-management.html) and overwrites a row's F/T/A/E only when the backend returns a non-zero score for that agent — so seeded demo numbers and live computed numbers can coexist until every agent has a real score.

There is a single AgentTable (partition key agentId, sort key sk). The scorer scans for entity rows only — sk = 'INFO' — then drops any agentId prefixed compliance:, aop:, or access:, and skips agents whose status is decommissioned. For each remaining agent it computes the four sub-scores and the overall, applies the NIST RMF modifier, and writes the results back onto the same INFO row as 0–100 integers (see §6 for the exact write shape).

Deployed today: The three core agents — management, discovery-scanner, and compliance-scanner — always deploy. Bedrock agents run on the us.anthropic.claude-sonnet-4-6 inference profile. The rai-scorer is a plain Lambda (not an AgentCore runtime); the compliance-scanner is a separate daily auditor that produces A–F audit reports — it does not write RAI scores (see §7).

1. Fairness (25% weight)

⚖️
Goal: Detect and prevent biased or unfair outputs from agents.

What the scorer does today REAL, BASE UNTIL SIGNALS

Reads the CloudWatch metric AWS/Bedrock/Guardrails → InvocationsIntervened, dimensioned by GuardrailArn, and the agent's own requests/errors fields from its DynamoDB INFO row. It starts from a base of 95 and penalizes for the intervention rate and error rate. In a fresh account the guardrail metric returns 0 and requests defaults to 1, so the score sits at 95.

Actual code assetsSrc/lambda/rai-scorer/index.py

def score_fairness(agent):
    invocations = agent.get('requests', 0) or 1
    errors = agent.get('errors', 0)
    error_rate = errors / max(invocations, 1)

    # Bedrock Guardrail interventions (no datapoints until a guardrail is
    # attached to the agent AND its ARN is on the record as guardrailArn)
    guardrail_interventions = float(get_metric(
        'AWS/Bedrock/Guardrails', 'InvocationsIntervened',
        _guardrail_dims(agent)) or 0)
    intervention_rate = guardrail_interventions / max(invocations, 1)

    # Base 95, penalized by intervention rate and error rate
    score = 95 - (intervention_rate * 100 * 0.5) - (error_rate * 100 * 0.3)
    return max(50, min(100, round(score)))

Still to harden TODO

  • Attach a Bedrock Guardrail to each agent and record its ARN as guardrailArn on the agent record, so InvocationsIntervened can be read for it. An agent with no guardrail produces no datapoints, which the scorer treats as no signal (its existing score is preserved) rather than as a bad score.
  • Invocation-log sampling — enable Bedrock model invocation logging to S3, sample input/output pairs, and run a bias classifier for demographic disparity.
  • Human feedback loop — persist operator thumbs-up/down; disproportionate negative feedback on an input category is a fairness signal.

2. Transparency (25% weight)

🔍
Goal: Ensure agent decisions are auditable and traceable.

What the scorer does today REAL, BASE UNTIL SIGNALS

Calls cloudtrail:LookupEvents filtered by the ResourceName attribute (the agentId, and a fallback lookup for agent-handler), and scales a base of 80 up toward 100 as CloudTrail coverage grows (20+ events/day = full coverage). It is deliberately blunt — it counts events, it does not distinguish event types or check whether invocation logging is enabled. With no CloudTrail history the count is 0 and the score sits at 80.

Actual code assetsSrc/lambda/rai-scorer/index.py

def score_transparency(agent):
    resource_id = agent['agentId']
    trail_events = count_cloudtrail_events(resource_id)

    # Fallback lookup on the shared handler name if the agent has no events
    fn_events = count_cloudtrail_events("agent-handler") if not trail_events else trail_events

    total_events = trail_events + fn_events
    coverage = min(total_events / 20, 1.0)   # 20+ events/day = full coverage

    score = 80 + (coverage * 20)             # base 80, up to 100
    return max(50, min(100, round(score)))

Still to harden TODO

  • Distinguish event types — verify bedrock:InvokeAgent, bedrock:InvokeModel, and lambda:Invoke events actually exist per agent, rather than counting any event mentioning the name.
  • Check invocation logging is enabled — call GetModelInvocationLoggingConfiguration and reward agents whose full input/output logging to S3/CloudWatch Logs is on. This requires adding bedrock:GetModelInvocationLoggingConfiguration to the scorer role (not granted today).
  • Agent trace visibility — reward enableTrace on agent invocations so operators can see why a decision was made. With AgentCore, prefer Observability OTEL spans.
  • Log-group existence — logs:DescribeLogGroups for the agent's Lambda (not granted today).

3. Accountability (25% weight)

📋
Goal: Ensure failures are handled properly and someone is responsible.

What the scorer does today REAL, BASE UNTIL SIGNALS

Computes an error rate from the INFO row's requests/errors fields, and queries AWS/Lambda → Errors for the shared function name AgentHandlerFn over 7 days purely to confirm error monitoring exists (a small +2 bonus). It starts from a base of 95. It does not yet verify DLQs, alarms, or ownership. In a fresh account the error rate is 0, so the score sits at 95 (or 97 with the monitoring bonus).

Actual code assetsSrc/lambda/rai-scorer/index.py

def score_accountability(agent):
    invocations = agent.get('requests', 0) or 1
    errors = agent.get('errors', 0)
    error_rate = errors / max(invocations, 1)

    # Confirm error monitoring exists (shared handler name), 7-day window
    error_log_events = get_metric(
        'AWS/Lambda', 'Errors',
        [{'Name': 'FunctionName', 'Value': 'AgentHandlerFn'}],
        stat='Sum', hours=168)
    has_error_monitoring = 1 if error_log_events is not None else 0

    # Base 95, penalize error rate, small bonus for monitoring
    score = 95 - (error_rate * 100 * 0.8) + (has_error_monitoring * 2)
    return max(50, min(100, round(score)))

Still to harden TODO

  • Per-agent Lambda error rate — query AWS/Lambda → Errors/Invocations by the agent's own FunctionName instead of the shared AgentHandlerFn constant.
  • Dead Letter Queue — lambda:GetFunctionConfiguration → check DeadLetterConfig exists (not granted today).
  • CloudWatch Alarms — cloudwatch:DescribeAlarms filtered by agent resources (not granted today).
  • Ownership + staleness — penalize INFO rows with no owner and a stale lastUpdated (> 180 days). The fields exist in the schema; the scorer does not read them yet.

4. Ethics (25% weight)

🧭
Goal: Ensure agents avoid harmful content and protect PII.

What the scorer does today REAL, BASE UNTIL SIGNALS

Reads the same AWS/Bedrock/Guardrails → InvocationsIntervened metric twice, narrowed by GuardrailPolicyType: ContentPolicy for harmful-content blocks and SensitiveInformationPolicy for PII redaction. It starts from a base of 93, adds a small +3 bonus for active PII protection, and penalizes only when the block rate is very high (> 5%). In a fresh account both metrics are 0, the PII-protection flag is still set (because guardrail_blocks >= 0 is trivially true), and the score sits at 96.

Actual code assetsSrc/lambda/rai-scorer/index.py

def score_ethics(agent):
    invocations = agent.get('requests', 0) or 1

    # Same metric, narrowed by policy type: ContentPolicy = harmful content
    guardrail_blocks = float(get_metric(
        'AWS/Bedrock/Guardrails', 'InvocationsIntervened',
        _guardrail_dims(agent, [{'Name': 'GuardrailPolicyType',
                                 'Value': 'ContentPolicy'}])) or 0)
    block_rate = guardrail_blocks / max(invocations, 1)

    # SensitiveInformationPolicy = PII redaction
    pii_redactions = float(get_metric(
        'AWS/Bedrock/Guardrails', 'InvocationsIntervened',
        _guardrail_dims(agent, [{'Name': 'GuardrailPolicyType',
                                 'Value': 'SensitiveInformationPolicy'}])) or 0)
    has_pii_protection = 1 if pii_redactions > 0 or guardrail_blocks >= 0 else 0

    # Base 93, +3 for PII protection, penalty only for a high block rate
    score = 93 + (has_pii_protection * 3) - (max(block_rate - 0.05, 0) * 100 * 0.5)
    return max(50, min(100, round(score)))

Still to harden TODO

  • Configuration checks over runtime metrics — call bedrock:GetAgent to verify a guardrail is actually attached, and bedrock:GetGuardrail to confirm content, PII, and denied-topic policies are configured. Neither action is on the scorer role today. An agent with no guardrail should drop hard, not sit at 96.
  • Fix the trivially-true PII flag — guardrail_blocks >= 0 is always true, so the +3 bonus is unconditional. Gate it on real PII-redaction activity or on a verified guardrail policy.
  • Metric names (resolved). There is no GuardrailBlocked or GuardrailPiiRedacted metric, and no AgentId dimension — earlier versions of this scorer queried those and silently got nothing back. The real metric is InvocationsIntervened in AWS/Bedrock/Guardrails, dimensioned by GuardrailArn/GuardrailVersion with an optional GuardrailPolicyType: see the Guardrails CloudWatch metrics reference.

5. System-Level: NIST RMF Modifier

🏛️
Goal: Weak system-level risk posture should drag down all agent scores.

What the scorer does today REAL, DDB-BACKED

Reads the compliance:nist-sp800-37 INFO row from the AgentTable, takes its complianceScore (default 90), and derives a multiplier in [0.90, 1.0]. The overall score is then max(50, round(weighted_average * rmf_modifier)). If the record is missing the modifier defaults to 1.0.

def get_rmf_compliance_score():
    item = table.get_item(
        Key={'agentId': 'compliance:nist-sp800-37', 'sk': 'INFO'}).get('Item')
    if item:
        rmf_score = float(item.get('complianceScore', 90))
        # 100 -> 1.0, 80 -> ~0.96, 60 -> ~0.92
        return max(0.90, min(1.0, 0.80 + (rmf_score / 500)))
    return 1.0

Still to harden TODO

Tie the modifier to a real AWS security posture instead of a seeded DynamoDB record — e.g. derive it from AWS Security Hub findings (securityhub:GetFindings) or AWS Config rule compliance (config:DescribeComplianceByConfigRule). Both actions would need to be added to the scorer role (not granted today).

6. What the Scorer Writes (DynamoDB shape)

The rai-scorer writes its results back onto each agent's INFO row as an UpdateItem — five 0–100 integers plus a timestamp. This is the row the data-handler serves on GET /agents and the UI renders:

table.update_item(
    Key={'agentId': agent['agentId'], 'sk': 'INFO'},
    UpdateExpression=('SET score=:s, fairness=:f, transparency=:t, '
                      'accountability=:a, ethics=:e, raiUpdatedAt=:ts'),
    ExpressionAttributeValues={
        ':s': overall, ':f': fairness, ':t': transparency,
        ':a': accountability, ':e': ethics,
        ':ts': datetime.utcnow().isoformat() + 'Z',
    })

The data-handler's _AGENT_FIELDS allowlist explicitly includes score, fairness, transparency, accountability, and ethics — otherwise these values would be written to the table but filtered out before reaching the UI.

Note — two different RAI schemas exist in this repo. The shipped rai-scorer above writes flat 0–100 integers onto the INFO row. Separately, flowamp_tools.compliance.write_rai_score() defines a distinct append-only RAI#<ts> row shape — { subScores, overall (a string in [0.0,1.0]), source, createdAt }. No shipped agent currently calls write_rai_score(); the compliance-scanner writes AUDIT# rows, not RAI rows. The RAI# path is available for a future agent-driven scorer but is not wired into the daily pipeline today. If you adopt it, reconcile the 0–100-integer vs. 0.0–1.0-string mismatch and teach the UI/data-handler to read the RAI# rows.

8. CDK Wiring (as deployed)

From cdk/lib/team-stack.ts — the scorer, its schedule, its on-demand route, and the exact IAM it holds today:

// ─── RAI Scorer (daily) ───
const raiScorerFn = new lambda.Function(this, "RaiScorerFn", {
  runtime: lambda.Runtime.PYTHON_3_12,
  handler: "index.handler",
  code: lambda.Code.fromAsset(path.join(assetsSrc, "lambda", "rai-scorer")),
  environment: { AGENT_TABLE_NAME: agentTable.tableName },
  timeout: cdk.Duration.seconds(120),
});
agentTable.grantReadWriteData(raiScorerFn);
raiScorerFn.addToRolePolicy(new iam.PolicyStatement({
  actions: ["cloudwatch:GetMetricStatistics", "cloudwatch:ListMetrics"],
  resources: ["*"],
}));
raiScorerFn.addToRolePolicy(new iam.PolicyStatement({
  actions: ["cloudtrail:LookupEvents"],
  resources: ["*"],
}));

// Daily schedule (a rate, not a fixed cron hour)
new events.Rule(this, "RaiScorerSchedule", {
  schedule: events.Schedule.rate(cdk.Duration.days(1)),
}).addTarget(new targets.LambdaFunction(raiScorerFn));

// On-demand re-score from the UI: POST /rai/score → same Lambda
raiApi.addResource("rai").addResource("score")
  .addMethod("POST", new apigateway.LambdaIntegration(raiScorerFn),
             authedMethodOptions);

IAM the scorer would need for the hardening TODOs

The role today holds only DynamoDB read/write, cloudwatch:GetMetricStatistics/ListMetrics, and cloudtrail:LookupEvents. To implement the configuration-based checks in §1–5 you would add:

raiScorerFn.addToRolePolicy(new iam.PolicyStatement({

}));

9. How the UI Renders RAI

The Responsible AI Scores panel lives in assetsSrc/site/agent-management.html:

  • renderAIScores(data) draws the fleet: an average/at-risk summary, a score-distribution histogram, and per-agent rows. Each row shows four thin bars labeled F, T, A, E (from a.fairness / a.transparency / a.accountability / a.ethics) and the overall a.score. Rows are color-banded (≥95 green, ≥92 blue, else amber) and split into Top Performers / Needs Attention.
  • The agent-detail view draws the same four dimensions as labeled bars — Fairness (blue), Transparency (purple), Accountability (orange), Ethics (green).
  • rescoreRai() backs the "⟳ Re-score now" button. It calls POST /rai/score, then fetchLiveData() and re-renders, toasting "Re-scored N agents" from the Lambda's {updated, total} result.
  • fetchLiveData() merges live GET /agents rows into the seeded aiScoresData by name, and only overwrites F/T/A/E when the backend returns a truthy score — so a freshly discovered agent with 0/absent metrics does not blank the seeded view.

10. Summary: Real Now vs. Still-to-Harden

Pillar Real signal today Base value in a fresh account Still to harden
Fairness CW AWS/Bedrock/Guardrails InvocationsIntervened + DDB error rate 95 Attach guardrails; verify metric dimension; log sampling + feedback
Transparency CloudTrail LookupEvents by ResourceName 80 Per-event-type check; invocation-logging check; trace visibility
Accountability DDB error rate + AWS/Lambda Errors (shared fn) monitoring flag 95 (97 with monitoring bonus) Per-agent fn metrics; DLQ + alarm + owner + staleness checks
Ethics CW InvocationsIntervened by GuardrailPolicyType (Content / SensitiveInformation) 96 Guardrail-attached/policy config checks; fix trivially-true PII flag
System (NIST RMF) DDB compliance:nist-sp800-37 record → 0.90–1.0 modifier 1.0 (if record absent) / ~0.98 at seed 90 Tie to Security Hub or AWS Config compliance
💡 Key insight: The high base values are a design smell, not a bug — a fresh, un-exercised agent scores ~90+ simply because none of the penalty signals have fired yet. Production hardening should shift the scorer from "penalize observed bad behavior" toward "reward verified good configuration" (guardrail attached? invocation logging on? DLQ + alarm present? owner assigned?). A well-configured agent with no incidents should out-score a poorly-configured one that just hasn't been caught yet.
