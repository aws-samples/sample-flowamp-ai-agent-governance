🧠 Amazon Bedrock AgentCore — FlowAMP Developer Guide

FlowAMP · AI Agent Governance on AWS · How the platform uses AgentCore today, and what to adopt next

What this guide is: FlowAMP is an AI Agent Governance platform, deployed with AWS CDK, that discovers, classifies, audits, and cost-accounts the AI agents running in an AWS organization. Governance is agent-driven: FlowAMP's own AgentCore (Strands) agents govern the account's other agents. This guide documents the AgentCore services FlowAMP actually uses today (Runtime + CloudWatch/CloudTrail observability), and — for the services it does not yet use — describes how you would adopt each one next. It is written against the real repo: see cdk/lib/agent-bundle.ts and cdk/lib/team-stack.ts.

Current state: FlowAMP uses two execution surfaces. The management agent is an AgentCore Harness — model, system prompt and tools as configuration, with AgentCore running the agent loop and no code bundle at all — and it reaches its tools through an AgentCore Gateway fronting the agent-handler Lambda as MCP tools. The two scanners are AgentCore Runtimes (direct-code deploy) because they are real Python programs with custom tools, DynamoDB writes and cross-account calls, which a harness cannot host. Up to three optional sample workload harnesses deploy behind deploySampleAgents=true. Harness Memory is on by default (session history), Evaluations are provisioned per core agent at runtime, and observability covers CloudWatch runtime logs/metrics, CloudTrail, and vended Gateway logs (plus X-Ray traces when enableTransactionSearch=true). The sections below map the remaining services to what you would adopt next.

1. AgentCore Runtime → Agent Execution ✓ DEPLOYED

Current (real): FlowAMP deploys three core / always-on agents on every deploy (no flag) across two execution surfaces — one harness and two runtimes:

  • management agent — a harness declared in cdk/lib/team-stack.ts (no agent source of its own) that answers natural-language questions over the AgentTable, calling the agent-handler Lambda's read operations as MCP tools through an AgentCore Gateway.
  • discovery-scanner (assetsSrc/agents/discovery-scanner/) — enumerates the account's AgentCore runtimes and LLM-classifies them (see §3).
  • compliance-scanner (assetsSrc/agents/compliance-scanner/) — runs the deterministic compliance-checks framework plus LLM judgment and audits the agents it finds (see §7).

Up to three optional sample workload harnesses (claims-triage, supply-chain, request-intake) deploy behind -c deploySampleAgents=true, giving discovery genuine agents to find. They declare no tools, and allowedTools: [] is set explicitly: left unset it defaults to *, which also grants the harness's built-in shell and file_operations tools. All agents run model us.anthropic.claude-sonnet-4-6 via an inference profile.

How the RUNTIMES are deployed — AgentCore direct code deployment (Lambda-style shared responsibility). Harnesses need none of this: they are pure configuration, so nothing is bundled for them. The two scanner runtimes use AgentRuntimeArtifact.fromCodeAsset with AgentCoreRuntime.PYTHON_3_12. AWS provides the Python language runtime; you must vendor your dependencies into the uploaded zip. fromCodeAsset uploads the directory as-is and does not run pip — a bundle with only a bare requirements.txt would crash at runtime with ModuleNotFoundError even though the runtime shows READY.

cdk/lib/agent-bundle.ts solves this at synth time, with no Docker: it copies the agent source + any shared packages (flowamp_tools, flowamp_compliance_checks) into a staging bundle, then vendors the arm64/cp312 wheels into it with uv. A recent boto3>=1.40 is vendored because the bedrock-agentcore-control service model postdates boto3 1.35.

# cdk/lib/agent-bundle.ts — vendor arm64/cp312 deps INTO the bundle (no Docker, no pip at runtime)
uv pip install \
  --python-platform aarch64-manylinux2014 \
  --python-version 3.12 \
  --target <bundle-dir> \
  --only-binary=:all: \
  -r requirements.txt
# then the agent's main.py + shared flowamp_tools / flowamp_compliance_checks
# are copied in, so the uploaded zip is fully self-contained.
// cdk/lib/team-stack.ts — a real AgentCore Runtime (Strands, direct-code deploy)
const agentcore = require("@aws-cdk/aws-bedrock-agentcore-alpha");

const discoveryScanner = new agentcore.Runtime(this, "DiscoveryScannerRuntime", {
  runtimeName: "flowampDiscoveryScanner",
  agentRuntimeArtifact: agentcore.AgentRuntimeArtifact.fromCodeAsset({
    path: assembleAgentBundle({
      agentDir: path.join(assetsSrc, "agents", "discovery-scanner"),
      sharedDir,
      sharedPackages: ["flowamp_tools"],
      stagingRoot: bundleStagingRoot,
      bundleName: "discovery-scanner",
    }),
    runtime: agentcore.AgentCoreRuntime.PYTHON_3_12,
    entrypoint: ["main.py"],
  }),
  environmentVariables: { AGENT_TABLE_NAME: agentTable.tableName, /* … */ PORT: "8080" },
  description: "FlowAMP discovery scanner — discovers and classifies AgentCore runtimes",
});
discoveryScanner.addToRolePolicy(modelInvokeStatement);
// RuntimeArn is surfaced as a CfnOutput (DiscoveryScannerRuntimeArn) for the invoker Lambda.

Adopt next: the management agent is a harness, reached through the api-handler Lambda via InvokeHarness; the scanner runtimes are invoked through small invoker Lambdas (discovery-scan-invoker, compliance-scan-invoker) because a runtime has no HTTP API of its own. You could front the runtimes with AgentCore Runtime endpoints + bidirectional streaming and retire some of that Lambda glue.

2. AgentCore Observability → Traces & Monitoring ✓ USED

Current (real): FlowAMP already uses CloudWatch and CloudTrail as its observability substrate:

  • Each AgentCore runtime writes to its own CloudWatch log group; the agents log control-plane calls and decision traces (e.g. list_agent_runtimes: N runtime(s) returned) so failures are diagnosable rather than paraphrased by the LLM.
  • The discovery-scanner emits a custom CloudWatch metric FlowAMP/DiscoveryScanner / AgentsDiscovered on each committed scan.
  • The rai-scorer Lambda reads cloudwatch:GetMetricStatistics / cloudtrail:LookupEvents to derive Responsible-AI signals; the compliance-scanner's deterministic checks also read CloudWatch metrics, CloudTrail events, and log groups.

Adopt next: AgentCore Observability adds first-class OpenTelemetry (OTEL) traces for every agent step — model calls, tool invocations, memory reads, guardrail checks — with per-runtime latency/token/tool-call breakdowns. Wiring it in would let the Trace Explorer read real OTEL spans instead of the current CloudWatch/CloudTrail-derived view, and give the RAI/compliance scanners richer, per-step evidence.

3. AgentCore Registry → Agent Catalog (currently DynamoDB + the discovery-scanner)

Current (real): the catalog is the single DynamoDB AgentTable (PK agentId, SK sk; entity rows use sk="INFO"). It is populated by real discovery, not by mock seed data (the demo seed is off by default, behind seedSampleData=true). The discovery-scanner runtime owns single-account native discovery: it calls bedrock-agentcore:ListAgentRuntimes, classifies each runtime into add / enrich / refresh / inactivate, LLM-infers displayName / category / riskTier / capabilities / suggestedOwner for new agents (flagged aiInferred: true, landing pending-review), and writes normalized INFO rows plus a baseline compliance assignment. The discovery-handler Lambda adds cross-account org discovery + (simulated) external connectors.

# discovery-scanner/main.py — enumerate live AgentCore runtimes (the real API call)
agentcore_client = boto3.client('bedrock-agentcore-control', region_name=_region)
response = agentcore_client.list_agent_runtimes(**kwargs)   # bedrock-agentcore:ListAgentRuntimes
agents.extend(response.get('agentRuntimes', response.get('agentRuntimeSummaries', [])))

Adopt next: AgentCore Registry is a managed catalog for agents, MCP servers, tools, and skills, with governed publish/review/approve workflows and hybrid semantic + keyword search. FlowAMP could register discovered agents into Registry and treat the DynamoDB table as a governance-annotation extension (owner, risk tier, compliance state) layered over the managed source of truth — rather than being the source of truth itself.

4. AgentCore Gateway → Tool Access adopted

Current: the management harness reaches its tools through an AgentCore Gateway with a Lambda target (agent-handler), which exposes the registry read operations as MCP tools with SigV4 inbound auth. The tool schema is declared inline in CDK; the old openapi.json is gone. The scanner runtimes call AWS control-plane APIs directly with scoped IAM (they are not fronted by a Gateway). External-platform integration lives in the discovery-handler Lambda (Microsoft/Okta/MuleSoft connectors are simulated today).

Adopt next: the Gateway is in place for the registry tools. Still available: semantic tool search (so an agent finds the right tool among many), interceptors, and JWT inbound auth if per-user identity needs to reach the tools — note SigV4 does not propagate the caller identity, so FlowAMP authorizes per user at the API Gateway/Cognito edge instead.

  • agent-handler is exposed as MCP tools through a Gateway Lambda target, replacing the action group + OpenAPI spec.
  • Connect the (currently simulated) external connectors to real external MCP servers.
  • Gate cross-agent tool calls with Gateway auth + interceptors instead of bespoke invoker Lambdas.
# Gateway converts your Lambda into an MCP tool — no OpenAPI spec needed
aws bedrock-agentcore-control create-gateway \
  --name "flowamp-gateway" \
  --authorizer-type "IAM" \
  --targets '[{
    "name": "agent-management-tools",
    "lambdaTargetConfig": {
      "lambdaArn": "arn:aws:lambda:us-east-1:123456789:function:AgentHandlerFn"
    }
  }]'

5. AgentCore Memory → Session & Long-Term (currently stateless)

Current: agent invocations are effectively stateless across calls. The discovery-scanner holds an in-memory scan working-set at module scope for the lifetime of a warm runtime, but there is no managed conversation memory. The UI "Conversation Store" is not backed by a memory service.

Adopt next: AgentCore Memory provides short-term (multi-turn) and long-term (cross-session) memory, shareable across agents. The management agent's chats and the scanners' prior-observation context could persist there instead of being reconstructed each run.

6. AgentCore Identity → Agent Auth (currently Cognito on the API, IAM on the runtimes)

Current (real): the UI/API is gated by a Cognito user pool authorizer (a single seeded flowadmin user in the demo; corporate SSO is a placeholder). AgentCore runtimes authenticate agent-to-AWS calls with scoped IAM role policies — the discovery/compliance scanners get least-privilege List/Get/Describe on Bedrock + AgentCore + CloudWatch/CloudTrail and never mutate the agents they govern.

Adopt next: AgentCore Identity integrates with existing IdPs (Cognito, Okta, Azure Entra ID, Auth0) and issues scoped credentials to agents, with agent-to-agent auth. It would replace the placeholder SSO story and let the Access Control Matrix enforce role→agent permissions rather than display them.

7. AgentCore Policy (Cedar) → Governance Enforcement (currently deterministic checks + scoped IAM)

Current (real): governance is audited, not yet enforced at tool-call time. The compliance-scanner runtime runs the deterministic flowamp_compliance_checks framework (baseline / NIST AI RMF / ISO 27001 / SOC 2 / NERC-CIP) plus LLM judgment against each agent it audits, writing AUDIT# / RAI# rows the compliance and Responsible-AI surfaces read back. It reaches the agents it audits with read-only inspection APIs (bedrock:GetAgent, bedrock-agentcore:GetAgentRuntime, GetGuardrail, etc.). Agent Operating Policies are metadata rows today, not runtime interceptors.

Adopt next: AgentCore Policy uses Cedar to define fine-grained rules and integrates with Gateway to intercept tool calls before execution. FlowAMP's audited boundaries and escalation conditions could become enforced Cedar policies:

// Cedar policy: an agent can read but not mutate
permit(
  principal == Agent::"flowampDiscoveryScanner",
  action == Action::"invoke_tool",
  resource == Tool::"list_agent_runtimes"
);

forbid(
  principal == Agent::"flowampDiscoveryScanner",
  action == Action::"invoke_tool",
  resource == Tool::"delete_agent_runtime"
);

// Escalation: require human approval for high-risk actions
forbid(
  principal,
  action == Action::"invoke_tool",
  resource == Tool::"decommission_agent"
) when { context.riskTier == "critical" && !context.human_approved };

8. AgentCore Evaluations → Automated Testing (not yet used)

Current: not implemented as an AgentCore service. FlowAMP's Responsible-AI scoring is a scheduled Lambda (rai-scorer) plus the compliance-scanner's grading; there is no managed evaluation harness or CI/CD gate.

Adopt next: AgentCore Evaluations runs automated assessments on agent sessions/traces (task execution, edge-case handling, output reliability) whose results feed Observability. It could back a deployment gate before promoting any newly discovered agent out of pending-review, and provide structured A/B comparison for prompt changes.

9. AgentCore Code Interpreter → Sandboxed Execution (not yet used)

Current: Not used.

Adopt next: agents can execute Python/JS/TS in an isolated sandbox. Useful for the sample analytics-style workloads (e.g. claims severity math, supply-chain impact modeling) or for compliance evidence computed on the fly.

10. AgentCore Browser → Web Interaction (not yet used)

Current: Not used.

Adopt next: agents can interact with web apps (fill forms, navigate, extract data). Useful for discovering or governing agents that only expose a web/portal surface, or for sample workloads that need to pull from legacy web systems.

Key implementation details worth knowing

  • Direct code deployment is a shared-responsibility model. fromCodeAsset uploads your directory but never runs pip. If you add a Python dependency, it must be vendored into the bundle for linux/arm64 + cp312 — cdk/lib/agent-bundle.ts does this at synth with uv. uv must be installed on the synth/deploy machine; Docker is not required.
  • boto3 must be recent (≥ 1.40). The bedrock-agentcore-control service model (used for ListAgentRuntimes / GetAgentRuntime) postdates boto3 1.35, so an older boto3 makes the scanner report "service not available". The bundles vendor a current version automatically.
  • Single DynamoDB table. One AgentTable (PK agentId, SK sk) holds every row type: entity INFO rows plus EVENT# / AUDIT# / RAI# / COST# / REVIEW# / MODEL# / COMPLIANCE# sub-collection rows. Readers filter sk="INFO" for entity listings.
  • Model. All agents run us.anthropic.claude-sonnet-4-6 via an inference profile (least-privilege IAM scoped to that profile + base model ARN).
  • Least privilege & read-only governance. The scanners only List/Get/Describe/Invoke-for-self-description the agents they govern; they never delete or mutate them.
💡 Key insight: FlowAMP is a real, deployed AgentCore application, not a mockup — the three core Strands runtimes stand up on every cdk deploy and the discovery-scanner really enumerates and classifies the account's AgentCore runtimes via bedrock-agentcore:ListAgentRuntimes. What remains "aspirational" is the rest of the managed AgentCore surface (Gateway, Registry, Memory, Identity, Policy/Cedar, managed Evaluations), where FlowAMP currently uses custom Lambda/DynamoDB implementations. The migration path is to keep the single DynamoDB table as a governance overlay while shifting the source-of-truth and enforcement responsibilities onto the managed services.
